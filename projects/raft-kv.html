Raft KV Store

A fault-tolerant key-value store in Go, replicated across servers with the Raft consensus algorithm. It keeps serving reads and writes as long as a majority of servers are up and can reach each other.

01Overview

I built a Raft library from scratch (leader election, log replication and crash recovery), then built a replicated key-value service on top of it that supports Get, Put and Append.

The servers never talk to each other directly. Every operation, reads included, goes through the Raft log, so every replica applies the same operations in the same order. Because reads also go through the log, a leader that has been cut off from the majority can never serve stale data.

02Request path

  1. 01Submit

    A client sends the operation to any server and retries elsewhere if it isn't the leader

  2. 02Append

    The leader adds the operation to its log

  3. 03Replicate

    AppendEntries RPCs carry new entries to followers

  4. 04Commit

    Once a majority has the entry, it is committed

  5. 05Apply

    Every replica applies it in log order, skipping duplicates

  6. 06Reply

    The waiting handler is notified and responds to the client

03Consensus layer

  • Leader election

    Randomized timeouts (0.5–1.5 s) avoid split votes, and nodes only vote for candidates whose log is at least as up to date as their own.

  • Log replication

    Followers check the previous index and term before accepting entries and truncate any conflicting suffix. The leader backs off nextIndex until the logs match.

  • Commit rule

    The leader advances its commit index once a majority of matchIndex values reach an entry.

  • Crash recovery

    The current term, vote and log are persisted and restored when a node restarts.

04Key-value layer

  • Exactly-once operations

    Each client carries a random ID and a sequence number, so a request retried after a leader change is recognised and never applied twice.

  • No stale reads

    Get goes through the log like any write, so only a leader backed by a majority can answer it.

  • Leader discovery

    Clients try servers from a random starting point with back-off until a leader accepts the request.

  • No deadlocks

    A dedicated goroutine drains Raft's apply channel, while RPC handlers wait on per-index channels with a timeout.

06Also built

Peer-to-peer file sharing on a DHT. For CS 382 Network-Centric Computing (2023), I built a distributed hash table in Python over raw TCP sockets. Files are spread across peers with consistent hashing, and the system survives nodes leaving or crashing.

  • Consistent hashing

    Nodes and file names are hashed onto a ring of 216 IDs; each file belongs to the next node clockwise.

  • Join and leave

    New nodes find their place by forwarding lookups around the ring. A leaving node hands its files to its successor and links its neighbours together.

  • Replication

    Each node keeps a backup of its predecessor's files.

  • Failure recovery

    Nodes ping their successor every 0.5 s and track their successor's successor, so a crashed node is bypassed and its files are restored from the backup.
