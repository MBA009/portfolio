AI Coding Agent Permissions

When an AI coding agent asks "May I install this?" twenty to forty times a session, do developers still read the question? In a lab study with 10 CMU developers, they mostly stopped. Security-trained participants were no more careful at the prompt either: they rely on sandboxes and VMs to keep them safe.

01Question

AI coding agents like Claude Code, Cursor and Copilot now edit files, run shell commands, install packages and make network calls. The one thing standing between that autonomy and the developer's machine is the permission prompt: approve, deny, or allow always.

Prior work shows AI-generated code is often vulnerable and that agents can be hijacked through prompt injection, but not how developers actually make these approval decisions in the middle of real work. We asked how developers evaluate the prompts, whether repeated prompts wear down that scrutiny, and whether background changes the answer.

02Method

  1. 01Screen

    21 survey respondents; 10 selected, balanced between security-focused and general engineers

  2. 02Seed

    A Flask task manager with 5 functional bugs and 6 security vulnerabilities

  3. 03Instrument

    CLAUDE.md and hooks that fire 20–40 prompts: packages, external services, sample data, folder access

  4. 04Observe

    60-minute debugging session with screen recording and JSONL telemetry

  5. 05Interview

    25-minute stimulated-recall interview, then thematic coding

03Findings

10Developers observed
20–40Prompts per session
0%Fast approvers who recalled what they approved
  • Fatigue sets in early

    In the longest session, replies shrank to a bare "yes" by turn 13 of 65, and that "yes" later approved installing discord.py into a Flask web app.

  • Consent without memory

    One participant approved a security-testing package in three seconds, then said in the interview that they had never installed it.

  • Experts offload vigilance

    Security-focused participants normally work in VMs, Docker or plan mode. On a lab machine they assumed was isolated, they clicked through faster. General engineers, with no such safeguards, were the ones who read prompts.

  • Scope beats wording

    Participants approved anything that looked in scope for the project and only paused when a request clearly reached outside it.

  • The agent pushed back on the study

    In some sessions Claude flagged the injected instructions as deceptive and refused the suspicious requests, while still following ordinary ones.

04Recommendations

  • Risk-categorize prompts

    Show an in-scope file edit differently from a network call, a package install or access to .ssh. Identical prompts train identical answers.

  • Make safeguards the default

    If sandboxing and plan mode are the real defense, users shouldn't have to know to turn them on.

  • Summarize approvals after the session

    A session-end summary of everything approved gives developers a chance to catch what they waved through.

05Limitations & ethics

Ten master's students at one university is a small sample. Telemetry was captured for only 4 of the 10 sessions, the lab machine changed how cautious people were, and prompt frequency varied within each session rather than between groups, so fatigue can't be fully separated from order effects.

The study was approved by the CMU IRB. The injected instructions were a partial deception, disclosed at debriefing; no one withdrew. Audio was deleted after transcription and only de-identified transcripts were kept. This page leaves out participant quotes and session IDs.

06Report

The full report, Privacy and Security Risks in AI Coding Agent Workflows, covers the study apparatus, all four hypotheses, per-session telemetry and the interview protocol.
